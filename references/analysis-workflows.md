## 通用规则

- 只使用完整结算日，不将当日盘中数与完整日直接比较。
- 默认只和店铺自己的历史比，不使用 `rivalAvg` 或 `rivalGood` 作经营结论。
- 区分“平台官方指标”、“本次计算”和“推断”。输出时明确标记。
- 不把相关性写成因果。不能从现有数据验证的原因，写“需进一步验证”。
- 每个模块最终只给 0–2 个动作；没有明确异常时允许给出“今日无需动作”。

## 模块 2：日体检

### 适用

用户说“看看昨天店铺怎么样”、“今天有没有什么要处理”、“做日检”时使用。

### 取数

1. 运行 `home-table --date <D-6> --end-date <D> --raw`，其中 D 为最近完整日。
2. 运行 `grow-factor --date <D> --raw`，只用于拆解当日成交构成，不把组件相加当成 GMV。
3. 只有店铺级售后指标出现明显变化时，再运行 `refund-item-list --date <D> --limit 5 --raw` 查问题款。

### 计算

将 D 同时与 D-1 和近 7 日中位数比较：

- 结果：`payAmt` 支付金额、`netPaymentAmount` 净支付金额。
- GMV 因子：`uv` 访客数、`payRate` 支付转化率、`payPct` 客单价。
- 意向：`cartByrCnt` 加购人数、`cltItmCnt` 商品收藏人数。
- 售后：官方 `payAmtRfdRate` / `ordRfdRate` / `realPayrealRfdRate`，以及 `rfdSucAmt` 当日完结退款金额。
- 推广花费：`p4pExpendAmt`, `cubeAmt`, `feedCharge`, `adStrategyAmt`, `tkExpendAmt`。可计算“推广花费 / 支付金额”，但必须标注它不是利润率或 ROI。

优先解释变化来自流量、转化还是客单价。只有变化方向与结果一致时，才写“主要伴随因子”；不写“导致”。

### 退款硬规则

- `refund-item-list.itemCaseEndSucAmt` / `itemCaseEndSucCnt` 是本日完结的退款事件，可能来自往期订单。
- 不使用 `itemCaseEndSucCnt / itemOrdPayCnt1d` 或 `itemCaseEndSucAmt / itemPayAmt1d` 作为真实商品退货率。
- 当该比值超过 100% 时，这正是跨期的证据，不是“一款当日退了这么多”。

### 输出合同

1. **一句话结论**：昨天整体上升/下降/平稳，主要伴随因子是什么。
2. **核心表**：支付、净支付、访客、转化率、客单价，列出 D、D-1、近 7 日中位数和变化。
3. **意向/售后/推广扫雷**：只列异常和口径。
4. **今日动作**：0–2 条，每条写触发它的数据证据。
5. **不能判断**：列出缺失的成本、订单队列或广告归因数据。

## 模块 3：周复盘

### 适用

用户说“复盘上周”、“这周店铺怎么样”、“找本周结构性问题”时使用。

### 取数

1. 运行 `home-table --date <D-13> --end-date <D> --raw`，将近 7 个完整日与前 7 日比较。
2. 运行 `sale-shop-list --date <D-6> --end-date <D> --limit 20 --raw` 和 `item-list --date <D-6> --end-date <D> --limit 20 --raw` 查商品结构。
3. 运行 `refund-item-list --date <D-6> --end-date <D> --limit 20 --raw` 和 `evaluation-list --date <D-6> --end-date <D> --limit 20 --raw` 查售后与评价信号。
4. 广告深度结论留给模块 6；本模块只展示 sycm 中的推广花费与店铺结果，不写 ROI。

### 周指标

- 可加总：`payAmt`, `netPaymentAmount`, `payByrCnt`, `payItmCnt`, `rfdSucAmt` 以及各推广花费。
- 周访客不能由每日 `uv` 相加当成去重周 UV。只报“日均 UV”。
- 周转化率使用 `sum(payByrCnt) / sum(uv)` 作为加权近似，标注“按日汇总近似”。
- 周客单价使用 `sum(payAmt) / sum(payByrCnt)`。
- 商品集中度使用前 5 款 `payAmt` 占取回商品列表总额；若列表被 limit 截断，必须写“在取回样本内”，不写全店占比。
- 退款沿用通用跨期规则，周度也不用完结退款事件反推该周成交队列退货率。

### 输出合同

1. **周结论**：结果、效率、售后三句话。
2. **本周 vs 前周**：支付金额、净支付金额、日均 UV、加权转化率、客单价、完结退款金额、推广花费。
3. **结构变化**：商品、新品/老品、意向、复购中最大的 1–3 个变化。
4. **风险清单**：只列有证据的问题，每项附命令和字段。
5. **下周动作**：最多 2 条，区分“继续观察”和“需要改动”。

## 模块 4：测款专项

### 适用

用户说“看看新品能不能放量”、“哪些款值得继续测”、“分析某款”时使用。

### 取数

1. 运行 `new-product-overview --date <D> --raw` 看指定日汇总。单日成功；显式 7/30 日区间实测返回业务错误 1003，不能声称总览支持 7/30 日。
2. 运行 `new-product-trend --date <D> --raw` 看截至 D 的固定 30 日趋势。显式 7/30 日区间实测同样返回 1003。
3. 运行 `new-product-list --date <D-6> --end-date <D> --limit 50 --raw` 建立新品队列。列表 7/30 日调用都成功，但曾返回完全相同数据；未确认隐藏口径前只称“区间列表”。
4. 若用户给出商品 ID，在返回队列中定位该款；找不到则明确告知，不用相似标题替代。
5. 如需广告测款数据，交给模块 6 联合 `alimama-cli`；本模块不从 sycm 字段伪造广告点击率。

### 同队列对比

对每款取 `shopUvNew`, `addCartCntNew`, `addCartRateNew`, `collectCntNew`, `payByrCntNew`, `shopPayRateNew`, `payAmtNew`, `uvWorth`, `publishNewTime`。

- 使用本次返回的新品队列中位数/分位数做相对比较，不套用通用行业阈值。
- 流量样本过小时只写“数据不足”，不判定款式好坏。
- 高访客 + 高加购 + 低支付只能标记“意向到支付有损耗”，后续验证价格、尺码、详情页和库存。
- 高转化但低访客可列为“候选加流量”，但没有毛利和退货队列时不写“应直接放量”。
- 有成交但没有成本数据时，不判断赚钱。

### 输出合同

1. **新品队列概览**：有数据的新品数、样本中位数和数据完整度。
2. **候选表**：商品用 A/B/C 脱敏，列访客、加购率、支付率、支付金额、UV 价值和判定。
3. **四类标签**：数据不足 / 意向高待转化 / 候选加流量 / 已有成交待验证利润。
4. **下一步**：最多 2 个验证动作，不直接给出加预算/补库存结论。

## 模块 5：退货归因

### 适用

用户说“退款为什么高”、“哪些款退得多”、“做退货归因”时使用。

### 取数

1. 运行 `home-table --date <D-13> --end-date <D> --raw` 查店铺级退款指标趋势。
2. 运行 `refund-origin-analysis --date <D>`，把 D 日完结退款按原订单付款日、退款场景、付款至完结间隔拆开。
3. 需要逐笔核对时运行 `refund-all-list --date <D> --by case-end --raw`；记录含 `orderId`, `ordPayTime`, `caseEndTime`, `caseSceneType`, `refundRealAmt`。
4. 运行 `refund-item-list --date <D-6> --end-date <D> --limit 50 --raw` 取商品级完结退款事件。
5. 运行 `evaluation-list --date <D-6> --end-date <D> --limit 50 --raw` 仅作服务评价信号；若评价数据没有商品 ID 或正文，不强行与退款款关联。
6. 真实退货率按付款批次计算：分子只保留该付款批次最终发生的 `caseSceneType=退货退款` 订单/件，分母使用同一付款批次支付订单/件。排除未发货退款、未收货退款和已收货仅退款；观察窗口未成熟时标注“暂定”。

### 分析

- 店铺级优先报官方 `payAmtRfdRate`, `ordRfdRate`, `realPayrealRfdRate` 的日趋势和口径。
- 商品级按 `itemCaseEndSucAmt` 和 `itemCaseEndSucCnt` 排序，命名为“完结退款事件热点”，不命名为“退货率最高商品”。
- 汇总 `itemCaseEndSucReasonList` / `itemCaseEndSucReasonText` 中的原因。原因字段为自由文本时，保留原文类别并合并明显同义词，不自创原因。
- `itemSlrResCnt` 仅报平台/数据字段所表示的卖家责任数，不由 AI 自行判责。
- 单个商品的当日退款金额超过当日支付金额时，必须在表中显示“跨期事件，不可相除”。
- `refund-origin-analysis` 回答“某日完结退款来自哪天成交”，本身仍不是退货率。

### 输出合同

1. **店铺售后趋势**：官方退款指标、完结退款金额和口径提示。
2. **退款事件热点**：商品 A/B/C、完结金额、笔数、原因、卖家责任数、跨期警告。
3. **原因分布**：尺码/不想要/质量/物流等真实返回类别，显示笔数或出现次数。
4. **可执行验证**：最多 2 条，例如核查尺码表或抽检面料；没有成本/库存数据时不直接下架。
5. **不能得出**：分母未配齐时的真实成交队列退货率、退货损失和商品利润。

## 模块 6：广告 ROI

### 适用

用户说“广告花得值不值”、“哪些计划/关键词/商品应调整”、“复盘万相台 ROI”时使用。

### 依赖与停止条件

- 需要安装 `alimama-cli` Skill。依次查找 `~/.claude/skills/alimama-cli/scripts/alimama.sh`、`~/.codex/skills/alimama-cli/scripts/alimama.sh` 和同级 Skill 目录；都不存在则停止并说明依赖缺失。
- 先运行 `alimama.sh doctor`。未找到登录态时停止，不使用 sycm 的广告引导金额伪造计划 ROI。
- 只调用查询命令。不调用 `promo-off`，不停投、调价或改预算。

### 取数

1. `charge-summary --date <D-6> --end-date <D> --window 15 --raw`：场景花费。
2. `scene-daily --date <D-6> --end-date <D> --window 15 --raw`：按日的展现、点击、花费、成交、ROI。
3. `report-campaign`, `report-keyword`, `report-item` 使用同一日期和 `--window 15 --limit 50 --raw`，分别查计划、词、商品。`report-keyword` 必须用网页真实参数 `offset`、`orderField=charge`、`orderBy=desc`。
4. 运行 sycm `home-table` 取同期支付金额和净支付金额，只作店铺结果背景。

### 归因规则

- 所有报表使用同一转化窗口。不混用 1/7/15 日窗口的成交和 ROI。
- 距离 D 尚不满 15 天的数据标记“归因未完全成熟”，后续可回补；不把暂时低 ROI 当最终结果。
- 万相台归因成交与 sycm 全店成交口径不同，不强求相等。
- ROI 只表示归因成交金额/广告花费，不包含商品成本、退货、平台费用和人工。没有这些成本时不写“赚钱”。
- 用同期中位数/分位数找低效项，不套用一个通用 ROI 及格线。样本花费过小时不下结论。
- 在排名前计算“返回明细花费合计 / 对应场景总花费”。若覆盖明显不足，标记“分页/排序样本不完整”，不输出全账户最好/最差结论。
- `report-keyword` 若前 50 条花费合计远低于关键词场景花费，判定为排序/分页失败，不进入经营结论。

### 输出合同

1. **账户摘要**：总花费、归因成交、ROI、点击率、转化率，标明 15 日窗口和成熟度。
2. **场景表**：关键词/人群/全站的花费、成交、ROI 和占比。
3. **低效候选**：计划/关键词/商品用 A/B/C 脱敏，附花费、点击、成交、ROI 和样本警告。
4. **高效候选**：只写“候选保留/加流量验证”，不直接调预算。
5. **建议**：最多 2 条，默认是人工复核动作，不执行写操作。

## 模块 7：客服质检

### 适用

用户说“看客服回复质量”、“咨询都在问什么”、“做客服质检”时使用。

### 取数

1. `reception-list --date <D-6> --end-date <D> --limit 100 --raw`：接待元数据。
2. `evaluation-list --date <D-6> --end-date <D> --limit 100 --raw`：服务评价。
3. `inquiry-loss-list` 和 `slow-rsps-list` 同期取数，但它们可能长期返回 0 条；空表不证明“没有流失/慢响应”。
4. 只有用户允许读取对话正文时，运行 `fetch-recent --date <D> --limit 20 --out <local-json>`。文件仅保存本地，不进 Git。

### 分析

- 用 `isUnReply` 统计未回复会话，用 `isSellerFst` 区分买家发起/客服主动。
- `startTime` 到 `endTime` 是会话时段，不是首次响应时长。没有消息级时间配对时，不评价“响应几秒”。
- 评价为空时记为“未评分”，不当作好评或差评。
- 对话主题用买家问题的意图归类（尺码、发货、物流、优惠、退换、材质、库存等），输出改写摘要，不逐字引用聊天。
- 不在输出中展示买家昵称、订单 ID、电话、地址或完整商品 ID。
- 对客服的负面判定必须同时有对话证据和服务结果；单凭会话长度、买家情绪或空评分不给人员贴标签。

### 输出合同

1. **接待摘要**：会话数、已回复/未回复、买家发起/客服主动。
2. **评价摘要**：有效评分数、空评分数和分布，不将空值当好评。
3. **咨询主题**：脱敏后的主题、出现会话数和一句概括。
4. **质检样例**：只展示改写后的买家问题、客服处理方式、好点/风险点，不显示原对话。
5. **改进动作**：最多 2 条，优先是话术/商品页信息改善；证据不足时不对个人进行绩效判定。
