# 字段字典 + 万能查询 — 设计文档 (spec)

> 2026-07-20。覆盖 sycm-cli 与 alimama-cli 两个仓库的一次大更新。
> 目标:把"字段知识锁在预设命令里、AI 要新字段只能等人焊按钮"改成
> "字典存量 + 方法论增量 + 自动写回 + 万能查询"四件套,让任何 AI 拿到 skill 就能自己查、自己学、自己更新。

## 1. 背景与问题

之前的模式:逆向一个页面 → 弄懂几个字段 → 焊死成一个专用命令。产生三个痛点(用户确认三个都是):

- **A 字段不全**:接口返回 62 个字段,命令只映射 32 个;alimama 报表接口"要什么给什么",但 CLI 写死了 17/21 个字段白名单。实例:19 列关键词日报缺"成交人数/自然流量转化金额/自然流量曝光量/引导访问潜客占比/成交新客占比" 5 列(后实查其中 2 列已在 raw 里,3 列缺字段码)。
- **B 命令不灵活**:一个页面一个命令,AI 无法自由选列/组合。
- **C AI 不知道能查什么**:字段码 ↔ 中文名 ↔ 属于哪个报表的对照,散落在历次对话里,没有机器可读的沉淀。

## 2. 方案总览(四件套)

| 件 | 是什么 | 解决 |
|---|---|---|
| ① 字段字典 | 每个 CLI 仓库一个静态字典文件,机器可读 | C(存量知识) |
| ② 发现方法论 | SKILL.md 里写三招"找字段的功夫" | C(增量能力) |
| ③ 写回规矩 | 探出的新字段必须写回字典,越用越厚 | 自更新、消耗只贵一次 |
| ④ 万能查询 | 命令支持任意字段码,不再受白名单限制 | A + B(动手能力) |

关系:字典像滚雪球——发布时给一颗大雪球(初稿),AI 每次探到新字段雪球变大;日常 95% 查询直接翻字典零思考,只有生字段才动脑,且只贵一次。

现有几十个预设命令**全部保留**,作为常用查询的快捷键,不拆。

## 3. ① 字段字典

**位置**:每个仓库各一份,`<skill>/fields.json`(sycm-cli 一份、alimama-cli 一份)。JSON 而非 YAML——CLI 是纯 Python 标准库 + requests 风格,不引 YAML 依赖。

**词条结构**:

```json
{
  "alipayInshopAmt": {
    "cn": "成交金额",
    "scope": ["report-*", "scene-summary"],
    "fmt": "amt",
    "status": "verified",
    "note": "总成交(直接+间接)"
  },
  "alipayInshopUv": {
    "cn": "成交人数(候选)",
    "scope": ["report-*"],
    "fmt": "int",
    "status": "candidate",
    "note": "2026-07-20 待 queryFieldIn 试探"
  }
}
```

字段说明:
- `cn` 中文名;`scope` 哪些命令/接口认它;`fmt` 数值格式(amt/int/pct/num,沿用 home-table 的四种);
- `status`:`verified`(实测确认)/ `candidate`(背出来或开源参考、未验证)。**只有 verified 才进格式化输出;candidate 仅在 --raw / 探测时使用**,防止假字段写进用户报表。
- `note` 口径备注(如"同日口径、女装低估真实退货率"这类坑要记在这)。

**初稿来源(三路汇流)**:
1. 现有命令里已验证的映射(sycm 32 项 + columns 元数据抓到的 + alimama 17+21 项)→ 直接 `verified`;
2. 模型已有知识背出的阿里系通用字段码 → `candidate`;
3. GitHub 开源项目(生意参谋爬虫/直通车对接)里的对照表 → `candidate`。

**首批验证目标**(用户 19 列日报的缺口):成交人数、自然流量转化金额、自然流量曝光量、引导访问潜客占比(确认 `inshopPotentialUvRate` 口径是否一致)、成交新客占比(确认 `newAlipayInshopUvRate` 口径)。

**隐私**:字典只含字段码/中文名/口径,**永远不含任何真实数值/店名**,可安全进公共库。

## 4. ② 发现方法论(写进两个 SKILL.md)

三招,按成本从低到高:

1. **翻响应自带的 columns 元数据**:sycm 列表类接口响应 `data.columns` 自带字段码+中文名(refund-item-list 实证)。`--raw` 拉一次,整页字段全收。
2. **queryFieldIn 试探**(alimama):往 `--fields` 里塞候选字段码,接口认就返回值,不认就报错/缺列。试错即发现。
3. **网页对照法**:登录网页看到目标数值/百分比 → `--raw` 全量拉 → 按数值反查字段码(cycleCrc 对照法,home-table 32 项实证)。用于前两招都够不到的场景。

方法论文本里必须写明**已知的坑**:单日广告数据归因未完成(用区间/`--no-realtime`)、同日退款口径低估真实退货率、macOS Chrome 多 profile 登录态。

## 5. ③ 写回规矩(写进两个 SKILL.md)

- 三招探出新字段并实测确认后,**必须**把词条以 `verified` 写回 `fields.json`,附验证日期与方法。
- 试探失败的候选也记一笔(`status: "rejected"` + note),防止后人重复踩。
- 字典文件变更随代码正常 commit;推公共库前照旧扫隐私(字典本身无隐私,流程不变)。

## 6. ④ 万能查询

不做全新命令,**给现有命令加通用参数**(改动最小、AI 心智负担最小):

**alimama-cli**:
- `report-*` / `scene-summary` 加 `--fields <逗号分隔字段码>`:替换默认白名单,直接塞进 `queryFieldIn`。未知字段码原样透传(这正是试探入口)。
- 加 `--all-fields`:请求字典里该 scope 的全部 verified + candidate 字段。
- 输出:verified 字段按字典中文名+fmt 格式化;candidate/未知字段仅在 `--raw` 中可见,格式化输出里以字段码原名列出并标注 `?`。

**sycm-cli**:
- `home-table` 加 `--fields`:从 62 个原始字段中任选(不再限 32 项);`--all-fields` 吐全部 62 个,字典有名的用中文名,没名的用字段码。
- 列表类命令加 `--columns`(沿用服务端 columns 命名):同理任选列。
- `api` 命令保留,作为最底层探测入口。

**macOS 多 profile 适配**(本次顺带,已确认是真 gap):sycm-cli / alimama-cli 读 Chrome cookie 支持指定 profile(环境变量 `SYCM_CHROME_PROFILE` / `ALIMAMA_CHROME_PROFILE`,或 `--chrome-profile` 参数),默认仍 `Default`。`doctor` 检测失败时提示"试试指定 profile"。

## 7. 错误处理

- `--fields` 含接口不认的字段码:alimama 侧接口若整体报错,降级为逐字段二分定位坏字段并明确报出("字段 X 不被接口接受");sycm 侧缺字段显示 `-`(沿用现状)。
- 字典文件缺失/损坏:命令不崩,退回内置默认白名单并 stderr 提醒。
- 字典与接口打架(字典说有、接口说无):以接口为准,提示该词条应降级,但**不自动改文件**——写回由 AI/人确认后做,防止误伤。

## 8. 测试

- 字典加载/损坏降级、`--fields` 参数拼装、candidate 不进格式化输出、`--chrome-profile` 传导:单元测试(mock,不打真接口)。
- 首批 5 个缺口字段的验证:实测(只读),结果写回字典。
